## 修复范围和边界

- 保留 Codex 桌面应用、IDE 和 CLI 入口；不替换为自定义启动器，不改写原始 JSONL。
- 保留既有话题映射、模型偏好、游标和去重记录。数据库新增状态或字段必须有迁移与旧数据测试。

- 不自动切换已有会话模型。新模型必须来自实际执行程序、实际账号的能力目录；支持的思考强度同样从目录读取。

- Codex 升级、生产数据库迁移、历史消息撤回和真实群验收属于部署操作，需在代码 PR 检查和合入后另行确认。

## 实施顺序和提交划分

### 第一阶段 建立失败用例

先为 F04、F05、F06、F07、F08 添加确定性故障注入测试，证明它们在基线上失败。再补 F01、F09、F10、F11 的输入和卡片快照测试。模拟时间和可控 Promise，不依靠随机网络、长时间 sleep 或真实用户群来触发竞态。

记录修复前后的 Codex 请求次数、任务状态、等待 Promise、结果发送映射和图片清理时机。不能仅通过改断言、增加重试次数或吞掉错误让测试通过。

### 第二阶段 修复执行与请求状态

依次修复 F04、F05、F06。目标是明确区分“Codex 已接受输入”“飞书确认已发送”“正在取消”“已确认中断”，并保证每个批准或问答请求仅结束一次。

F05 涉及任务和回合状态、Root 授权到期及服务退出处理，F06 涉及请求状态、超时和重启恢复。新增数据库状态前要同步检查 `CHECK` 约束、终态列表、查询、状态统计和旧数据库迁移，不能只修改一个 TypeScript 字段。

建议各问题分别提交可审查的 commit。此阶段完成后，再修改共用发送流程，避免把执行错误与展示错误混在一起排查。

### 第三阶段 修复结果发送

先处理 F08 的字节截断和独立附件发送，再处理 F07 的持久化发送状态与重发入口。执行失败、取消和发送失败应能被分别识别；重发结果不得调用 `turn/start`、`turn/steer` 或创建新任务。

保证 JSONL 导入、重启恢复与直接发送共用去重规则。针对请求已发送但响应丢失的情况，使用现有发送记录或可用的消息查询确认状态，不能承诺外部接口无法提供的绝对一次发送。

### 第四阶段 修复输入和卡片体验

处理 F01、F03、F09、F10、F11、F14；结合 F12 验收新旧话题中的操作入口。宿主上下文过滤与历史清理使用同一个识别规则，但不要把任意用户输入的 XML、代码块或引用误删。

普通权限提示建议为“可修改当前项目文件，不可联网”，详细规则按需查看。Plan 与 Root 使用各自实际权限说明，高权限风险与授权不得隐藏；当前回合和下一回合设置须区分。

### 第五阶段 更新模型目录和完成验收

在代码中处理 F02 的刷新、缓存和诊断；提供受控的独立 Codex 升级步骤，而不是在服务启动时自动升级。F13 独立修复测试兼容性，确保全项目测试恢复通过。

模型验收以 `gpt-6.1-sol` 为指定目标。按照 OpenAI Docs 核对，[官方变更日志](https://learn.chatgpt.com/docs/changelog)记录了 Sol 6.1 和 CLI 0.159.1 的目录更新。测试时仍以实际账号目录为准，不把 API 文档的可用性或思考强度列表直接写死为 Codex 能力。

新增回归测试必须覆盖：

- 同一追加输入在确认失败、重复事件和重启后不会再次执行。

- 纯宿主上下文、混合记录、真正用户 XML 和代码示例；历史清理部分失败后可继续。
- 新旧模型目录、刷新并发与失败、过期卡片提交、不同模型思考强度。

CardKit 创建草稿成功不等于消息发送接口接受，也不证明手机渲染正确。`npm run check:cards` 需要真实飞书凭据并创建远端草稿，只能在用户同意后补做；本计划没有自动运行该命令。

8. 记录验收结果后再宣布上线完成。回滚代码涉及新数据库状态时，先判断旧代码兼容性；恢复旧数据库会丢失部署后的数据，不能直接覆盖仍在写入的数据库。

### F01 宿主上下文被当作用户消息

优先级 P1。证据：实际记录确认、隔离复现。

**现象与原因。** 飞书展示“用户”后跟整段 `<recommended_plugins>`。这些插件推荐、环境信息和 AGENTS 指令是宿主传给模型的上下文，不是用户聊天。`isSyntheticHostMessage` 只去掉插件和环境标签后检查是否为空；混合记录还剩 AGENTS 指令时，检查失败，原文整段被发送。历史清理重复了同样的判断，而且 `migration.history_cleanup_v1=1` 后不再执行。

**位置。** [session-parser.ts](../../../tools/feishu-codex-bridge/src/session-parser.ts) 的 `isSyntheticHostMessage`、`textFromContent`、`parseJsonlChunk`；[sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `migrateTitlesAndSyntheticMessages`、`processFile`、`syntheticMessageId`。

**最小复现。** 将以下文本放入一个 `response_item`，其 `payload.type` 为 `message`、`role` 为 `user`、`content` 为 `input_text`；用 `parseJsonlChunk` 解析。目前得到 1 条可见消息，仍含插件列表。

```text
<recommended_plugins>plugins</recommended_plugins>
# AGENTS.md instructions
<INSTRUCTIONS>host rules</INSTRUCTIONS>
<environment_context>env</environment_context>
```

**修复要求。** 用共同的可见内容识别规则处理导入和历史清理。结合来源、结构和宿主消息边界识别注入内容，不以 `role=user` 或一个 XML 标签作为唯一依据。混合真实请求的记录应保留真实请求；用户主动发送的标签、引用和代码示例应保持可见。保留原始日志和原始去重 ID 或提供兼容映射，避免内容净化后重新导入旧消息。

**验收。** 纯插件、插件加环境、插件加 AGENTS 均不作为用户聊天发送；宿主上下文加真实问题只显示真实问题；用户讨论 `<recommended_plugins>` 的代码示例仍可见。历史清理支持只预览、明确确认、分项记录成功失败、失败重试和幂等重复执行，只操作机器人消息，不删除真实用户消息。升级迁移不能因为旧版标记为成功而漏过新候选。

### F02 模型目录未更新到 Sol 6.1

优先级 P1。证据：实际环境确认。

**现象与原因。** 飞书服务使用 Codex `0.154.0`，目录不含 `gpt-6.1-sol`；同账号同配置目录下，IDE 的 `0.159.2` 返回该模型。源码没有硬编码完整菜单，而是调用配置中的 `CODEX_BIN debug models`。目录只在启动或重试时刷新，缺少过期刷新机制。更新 Git 仓库并不更新这个外部程序。

**位置。** [codex.ts](../../../tools/feishu-codex-bridge/src/codex.ts) 的 `CodexCliProbe.listModels`、`parseModelCatalog`；[sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `refreshModels`、`cachedModels`、`modelBySlug`、模型卡片入口；[config.ts](../../../tools/feishu-codex-bridge/src/config.ts)；[doctor.mjs](../../../tools/feishu-codex-bridge/scripts/doctor.mjs)；[install.mjs](../../../tools/feishu-codex-bridge/scripts/install.mjs)。

**复现。** 读取服务实际 `CODEX_BIN` 与 `CODEX_HOME`，分别执行该程序及 IDE 程序的 `--version`、`debug models`，只比较模型 slug 和能力字段，不输出登录凭据。检查桥接缓存 `codex.model_catalog.v1`。目前刷新旧程序仍不能获得目标模型。

**修复要求。** 分成部署升级和目录管理两部分。升级独立 CLI 并保留回滚版本；不能依赖 IDE 的版本化路径或启动时自动下载最新版。目录保存刷新时间和来源版本，建议过期 30 分钟后异步刷新、打开模型菜单时检查过期，并保留明确的手动刷新入口。并发刷新共用一次请求，停止服务时清理计时器，设置诊断超时；失败使用最近一次有效缓存并提示过期，不用空结果覆盖有效目录。

**验收。** 新程序真实目录返回 Sol 6.1 后菜单可选且能执行获准的最小任务；`supported_reasoning_levels` 是 Codex 强度的依据，不硬编码 API 文档列表。既有会话不自动换模型。升级后旧目录中消失的模型明确提示重新选择；旧卡片提交按最新能力校验。缓存缺失、非法、刷新超时、并发刷新及版本变化有测试。doctor 显示实际执行路径、版本和目录状态，不泄露秘密。维护说明的修正建议保存在本地，本次代码 PR 不提交 README 改动。

官方依据：[OpenAI Docs 变更日志](https://learn.chatgpt.com/docs/changelog)记录了 Sol 6.1 在 Codex 的发布和 CLI 0.159.1 的目录更新。账号访问权与协议兼容仍需运行时验证；当前修复目标是 `gpt-6.1-sol`，不是自动更改默认模型。

### F03 权限提示难懂且应匹配实际任务

优先级 P2。证据：用户反馈、代码确认；新文案属于修复建议。

**现象与原因。** 根卡反复展示“Default：仅允许 canonical 工作目录写入，禁止网络。”`canonical` 指解析符号链接后的真实目录，但用户无法直接理解。`sessionCard` 根据模式和全局 `executionMode` 生成提示；全局 Root 配置的文案分支先于 Plan，配置支持 Root 与某轮真正获授权也不相同，需与 `resolveTurnExecutionPolicy` 的实际策略对齐。

**位置。** [cards.ts](../../../tools/feishu-codex-bridge/src/cards.ts) 的 `sessionCard`；[sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `sessionView`、`resolveTurnExecutionPolicy`、模型和模式切换入口；[execution-policy.ts](../../../tools/feishu-codex-bridge/src/execution-policy.ts)。

**修复要求。** 普通任务用“可修改当前项目文件，不可联网”。Plan 用“只读规划，不修改文件，不可联网”。细节按需查看，说明限制指任务沙箱，不是飞书与模型服务的连接。文案分别显示当前回合有效权限和下一轮设置，依据实际策略及授权状态，不能仅看全局配置。Root 的容器读写、联网和进程风险、预检失败及每任务授权仍须明显展示，不折叠掉关键风险。

**验收。** 默认卡片无 `canonical` 黑话和冗长重复规则；详情解释实际项目目录。权限变化有提醒。普通、Plan、Root 配置但未授权、Root 已授权、Root 预检失败、运行中修改下一轮设置均有测试，文案与执行参数一致。模式切换、详情入口和手机阅读完成验收。只改展示，不放宽实际沙箱或批准策略。

### F04 追加消息确认失败导致重复排队

优先级 P1。证据：隔离复现。

**现象与原因。** `continueSession` 把 `turn/steer` 和飞书确认放在同一个 `try` 中。Codex 已接受输入，飞书确认抛错，`catch` 仍清除跟踪及图片，并调用 `enqueueResumeTask`。复现结果是 Codex 接受 1 次、额外任务排队 1 次。

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `continueSession`、`queuePendingPrompt`、`dropPendingPrompt`、`rememberTurnImages`、`enqueueResumeTask`；[task-scheduler.ts](../../../tools/feishu-codex-bridge/src/task-scheduler.ts)；[db.ts](../../../tools/feishu-codex-bridge/src/db.ts) 的入站事件和任务去重。

**复现。** 模拟运行中的回合，让 `appServer.request('turn/steer')` 成功，再让 `respond` 抛出确认发送错误。统计 `turn/steer` 和后续排队次数，不启动真实 Codex。

**修复要求。** 分开输入接受状态和确认发送状态。确认失败只记录或重发确认，不能再次执行，也不能删除已交给当前回合的图片。Codex 请求明确拒绝、已确认成功和结果不确定应分别处理；请求超时不证明未执行，不得无条件转为新任务。用来源消息和回合的持久记录避免入站事件重试、重复回调及重启重复提交。

**验收。** Codex 成功加飞书失败时额外排队为 0，图片保留至回合结束；明确拒绝时只排队一次并正确清理未使用图片；响应丢失时显示待确认而不是自动重放。重复入站和重启不增加执行次数，JSONL 导入不把该输入再次显示为机器人“用户”消息。

### F05 取消失败却提前记录已中断

优先级 P1。证据：隔离复现。

**现象与原因。** `cancelSessionWork` 先取消数据库任务、删除活动回合、记录 `interrupted` 并清理图片，再异步调用 `turn/interrupt`。中断被拒绝时，仅有失败记录；真实任务可能仍运行，但后续流已失去活动状态。隔离复现中，中断失败、保存状态仍是 `interrupted`，活动状态已删除。

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `cancelSessionWork`、`cancelAllWork`、`expireRootGrants`、退出处理；[turn-coordinator.ts](../../../tools/feishu-codex-bridge/src/turn-coordinator.ts)；[db.ts](../../../tools/feishu-codex-bridge/src/db.ts) 的任务和回合状态；[types.ts](../../../tools/feishu-codex-bridge/src/types.ts)。

**修复要求。** 未开始任务可以直接取消；活动任务使用“正在取消”等过渡状态。中断 RPC 被接受不等于终态，应等待回合结束通知或可靠状态查询。保留回合、图片和后续通知处理，失败显示“取消失败”或“状态待确认”，不能显示已取消。协调 Root 授权过期、服务退出、取消全部和自然完成的竞争，不让正在取消的会话领取下一任务。

**验收。** 拒绝中断后仍可接收原任务输出，图片不提前删除；成功中断后只清理一次；自然完成与取消同时发生时保留实际终态。重复取消幂等，待执行任务不会误启动，授权回收仍有效。新增状态有 SQLite 迁移、统计和查询覆盖，重启后不把未知任务自动重放。

### F06 快速回答与超时使请求继续等待

优先级 P1。证据：隔离复现、代码确认。

**现象与原因。** `onAppServerRequest` 先发送卡片、保存请求并更新状态卡，最后才注册 `approvalService.waitFor(nonce)`。答案可能在更新状态卡的等待期间到达；`resolveRemoteRequest` 找不到等待处理器，就记为过期，之后新注册的 Promise 无人结束。另一问题是超时回调使用 `claimServerRequest`，但该方法拒绝 `expiresAt <= Date.now()`，因此定时器到期时可能直接返回，留下 `pending`。

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `onAppServerRequest`、`resolveRemoteRequest`、原生问答和批准回调；[approval-service.ts](../../../tools/feishu-codex-bridge/src/approval-service.ts) 的 `waitFor`、`take`、`clear`；[db.ts](../../../tools/feishu-codex-bridge/src/db.ts) 的 `claimServerRequest`、`expireServerRequests`。

**复现。** 在状态卡更新被可控 Promise 暂停时提交答案，再释放更新；断言 Codex 等待是否结束。另将请求到期时间设为过去，调用当前超时使用的领取方法，会返回空且请求仍为 `pending`。

**修复要求。** 在卡片可被操作前持久化请求并注册等待处理器；发送失败时回收请求、等待器和计时器。实现有明确到期条件的原子超时转换，与用户领取分开，不能复用拒绝到期请求的接口。超时、回答、取消、自然结束、app-server epoch 变化只能有一个获胜者；每条路径结束等待并清理资源。仅延后定时器或增大超时时间不是修复。

**验收。** 卡片发送前后快速回答、状态卡慢响应、重复回答、到期临界点、发送失败、服务退出和 epoch 改变均不挂起。超时产生正确协议的拒绝或取消结果。多问题按每个问题 ID 提交，保留当前多题修复；机密输入继续禁止。采用模拟时钟和可控 Promise 验证所有等待最终结束。

### F07 结果发送失败仍显示完成

优先级 P1。证据：隔离复现。

**现象与原因。** `turn/completed` 先把回合和任务记为完成，再调用 `finishTurnStream`。发送异常只写入 `finish_turn_stream` 失败记录，删除活动回合后仍把状态卡改为“完成”。复现结果为任务 `completed`、卡片“完成”、结果发送失败。

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `onAppServerNotification`、`finishTurnStream`、导入去重和恢复；[db.ts](../../../tools/feishu-codex-bridge/src/db.ts) 的回合、发送映射、失败记录；[cards.ts](../../../tools/feishu-codex-bridge/src/cards.ts) 的状态和操作入口。

**修复要求。** 执行状态与结果发送状态分别持久化。Codex 已完成但发送失败时显示“执行完成，结果发送失败”，提供“重发结果”。完整输出在发送成功前必须能可靠恢复；保存方式应有权限、保留期限和兼容迁移。卡片和附件分别记录成功状态，重发仅处理失败部分，不重新运行任务。

**验收。** 发送失败和部分成功不会丢正文、不会错误标为已送达；重发不调用任何执行 RPC、不创建新任务。重启后能恢复待发送输出，成功后 JSONL 不再次发送重复结果。附件失败不丢已成功卡片，反之亦然。区分执行失败、中断和结果发送失败；终端中断与服务关闭路径也检查。外部接口响应丢失时记录不确定状态，先查询或核对，不能简单重发并宣称绝对无重复。

### F08 长中文预览超限并阻止附件

优先级 P1。证据：隔离复现。

**现象与原因。** `inlinePreview` 用 UTF-8 字节判断是否超过 45,000，但用字符截取前 30,000 和后 10,000，短于这些字符预算时头尾还会重叠。`'中'.repeat(16000)` 原文为 48,000 字节，当前预览变成 78,076 字节。`finishTurnStream` 把附件放在卡片发送之后，卡片抛错则附件调用次数为 0。

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `inlinePreview`、`appendBoundedText`、`flushTurnStream`、`finishTurnStream`；[cards.ts](../../../tools/feishu-codex-bridge/src/cards.ts) 的 Markdown 处理；[feishu.ts](../../../tools/feishu-codex-bridge/src/feishu.ts) 的大小边界和分段发送。

**修复要求。** 按 UTF-8 字节截断且不破坏字符边界，防止头尾重叠；预算包括省略提示、Markdown 转义和序列化开销，不只检查原始字符串。卡片与完整 Markdown 附件独立尝试并记录结果；如果正文保存或附件暂时失败，F07 的重发能恢复。完整正文需单独可靠保存，不能把已经截断的展示缓存当作完整附件。核对 README 中“50,000 字符”的说法，将与实际限制一致的文档修正建议记录在本地，不加入代码 PR。

**验收。** ASCII、中文、emoji 和混合文本的边界测试保证有效 Unicode，预览与实际请求大小不超预算，首尾不重复，附件完整内容与原文一致。卡片失败仍尝试附件，附件失败仍保留卡片。测试流式、普通卡片和本地 JSONL 导入路径，不只修改一个 helper。

### F09 富文本链接和标题丢失

优先级 P2。证据：隔离复现。

**现象与原因。** `postContent` 只提取 `tag=text` 和 `tag=img`，忽略 `tag=a` 的 `text`、`href` 以及富文本标题。只包含一个链接的消息目前解析为 `text=''`，真实用户请求内容可能丢失。

**位置。** [feishu.ts](../../../tools/feishu-codex-bridge/src/feishu.ts) 的 `postContent`、`parseIncoming`；[feishu.test.ts](../../../tools/feishu-codex-bridge/test/feishu.test.ts)。

**最小输入。**

```json
{"zh_cn":{"title":"项目资料","content":[[{"tag":"a","text":"项目","href":"https://example.com/repo"}]]}}
```

**修复要求。** 在顺序正确的纯文本或 Markdown 表示中保留标题、段落、链接文字和 URL；避免遍历多语言对象时重复拼接多个语言版本。保留图片和提及清理，未知标签不导致异常或伪造内容，不主动访问 URL。

**验收。** 链接单独存在、标题加链接、多段文本混合图片、多语言、无标题、无效字段与提及均有测试。提取结果既含链接文字也含实际 URL，可作为正常续聊输入，不再提示空消息。

### F10 新建向导可能忽略普通输入

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的 `handleFeishuMessage`、向导输入动作；[feishu.ts](../../../tools/feishu-codex-bridge/src/feishu.ts) 的提及识别；[cards.ts](../../../tools/feishu-codex-bridge/src/cards.ts) 的新建向导；安装和 doctor 的事件权限检查。

**验收。** 有效向导普通输入、带提及输入、表单输入可按声明完成任务；非授权用户、其他群、无向导、过期向导不触发执行。话题内普通文字继续属于该 Codex 会话，不被主时间线向导劫持。消息投递限制通过真实飞书群验收，不用模拟收到事件证明平台一定投递。

### F11 会话卡片有字面量转义

### F14 暂停和重试的含义不清楚

**现象。** 暂停主要阻止同步或后续调度，不等于中断运行中的 Codex 回合。`/retry` 刷新目录、恢复基础设施并尝试同步，不等于重新执行所有失败任务或重新发送所有结果；当前“正在重试未完成任务”容易让用户误解。

**位置。** [sync-runtime.ts](../../../tools/feishu-codex-bridge/src/sync-runtime.ts) 的暂停、恢复、重试动作和命令；[task-scheduler.ts](../../../tools/feishu-codex-bridge/src/task-scheduler.ts)；[cards.ts](../../../tools/feishu-codex-bridge/src/cards.ts) 的控制台和帮助。

**验收。** 帮助、卡片与命令回复使用一致含义，测试暂停时活动任务、排队任务和恢复后的行为。重试连接不增加 `turn/start` 或 `turn/steer` 次数，失败结果不被误当成需要重跑的任务。
