# 飞书桥接交互逻辑审查（Claude 侧与 Codex 侧）

日期：2026-10-05
范围：只读审查，没有修改代码。

- Claude 侧：`main` 分支（提交 `1d1b5bf`，即本机正在运行的版本）。
- Codex 侧：`fix/codex-acceptance` 分支（提交 `08ea5c7`，包含尚未合并的 PR #3–#7）。

下文的行号都相对于仓库根目录。Claude 侧的代码在 `src/claude/`，Codex 侧主要在 `src/sync-runtime.ts`、`src/cards.ts`。

## 一、结论

1. **两侧最大的问题都出在“点了以后发生什么”上。**
   - Codex 侧有很多卡片按钮的处理结果不会替换被点的卡片，而是在群主时间线另发一张新卡（问题 X1）。
   - Claude 侧的问题是：话题里的 `/help`、`/model` 等命令会被当作发给 Claude 的消息，顺带把会话控制权切到手机（问题 C1）。

   这两条最常碰到，也最容易让人困惑，建议先修。
2. **两侧都有回调超时的风险。** 好几个按钮在回调里同步等待耗时操作，可能超过飞书 3 秒的回调时限（C5、X2）。超时后手机会提示出错，但操作其实已经执行，用户再点一次就可能重复新建会话或重复执行。
3. **Codex 侧的审批规则需要单独处理。**
   - 批准卡没有说明批准后命令会在沙箱外运行（未确认，见 X3）。
   - 自动拒绝规则一方面有误判，例如 `grep "async "` 会被当作 netcat 拦掉；另一方面又放行了 `git push`、`pip install` 等联网操作，与 README 的说法不一致。
4. **机器人菜单实际上不存在。** README 说安装器会自动配置菜单，但代码里没有写入菜单的逻辑，而且 Claude 侧需要的是 `claude.*` 事件键，文档里没有写（C2）。
5. **使用数据太少，不能作为依据。** 从绑定到现在，Claude 桥接一共只收到 16 条消息、34 次按钮点击，大部分发生在 10-02 开发调试期间（期间服务重启了十几次），看不出真实的使用障碍。本报告的结论主要来自代码审查。

## 二、交互地图（精简）

### 2.1 Claude 侧

| 入口 | 可做的操作 |
|---|---|
| 群主消息 | `/` 命令菜单、`/help`、`/home` 和 `/status`、`/sessions`、`/search <词>`、`/sync`、`/pause`、`/resume-sync`、`/new [目录] [任务]`；@机器人 后写文字，会存为草稿并让你选目录；不 @ 的文字会被**静默忽略** |
| 会话话题 | 桥接自己处理的只有 `/` 和 `/menu`、`/export`、`/stop`、`/deliver`、`/ls`；其余内容（包括 `/help`、`/model` 等）都交给 Claude；以 `>>` 开头的消息排到本轮结束后再发；有待回答的问题时，文字当作回答 |
| 卡片按钮 | 控制台、清理、帮助、命令菜单、最近会话和搜索、根卡片（停止本轮、权限模式、模型、导出、刷新）、权限请求、提问、计划、权限模式卡、模型卡、本机忙碌等待（立即切换、分叉、取消）、新建会话（选目录、填任务）、目录内容。**全部原地替换**，只有模型卡和权限模式卡会在话题末尾另发一张 |
| 机器人菜单 | 代码认识 `claude.home`、`service`、`sessions`、`search`、`new` 五个键，但菜单从来没有被配置过 |

### 2.2 Codex 侧

| 入口 | 可做的操作 |
|---|---|
| 群主消息 | `/`、`/help`、`/home`、`/status`、`/new`（4 步向导）、`/new <目录> <提示>`、`/projects`、`/sessions`、`/search`、`/sync`、`/pause`、`/resume-sync`、`/retry`、`/cancel`、`/model`；中文快捷词需要 @；@ 后写普通文字会被拒绝，提示用 `/new` |

| 卡片按钮 | 控制台、服务管理、帮助、新建向导（项目、模型、强度、任务）、最近会话、根卡片（修改模型、切换 Plan/Default、查看本轮审阅、权限说明）、运行状态（取消任务、重发结果）、取消归档、本机问题、原生提问、批准请求（批准一次、拒绝、取消回合、告诉 Codex 怎么做）、Root 授权。**结果的投递位置不统一**，见 X1 |
| 机器人菜单 | `codex.home`、`new`、`sessions`、`search`、`service`，同样没有配置 |

## 三、问题清单

影响程度分三档：
- 高：常用操作会遇到，并且会造成误操作或困惑。
- 中：会遇到，但有办法绕过。
- 低：边角情况，或只是文案问题。

### 3.1 两侧共同的问题

**S1（中）机器人菜单没有配置，文档说法不对。**
- 证据：
  - `src/installer.ts:22-28` 定义了 `FEISHU_MENUS`，但只有测试在引用它，`configureFeishuApp`（`installer.ts:105-140`）并不写入菜单。
  - README 第 46、88、283 行说安装器会“自动配置机器人菜单”。
  - Claude 侧代码只认 `claude.*` 事件键（`src/claude/runtime.ts:1452-1456`），但 `docs/claude.md` 完全没有提到菜单。
- 建议：先改文档，写明需要手工配置菜单，Claude 侧用 `claude.*`、Codex 侧用 `codex.*`。飞书开放平台如果有写入菜单的接口，再让安装器自动配置（接口未确认）。收到不认识的菜单键时打一条警告日志。

### 3.2 Claude 侧

**C1（高）话题里发 `/help`、`/model`、`/status` 会交给 Claude，并切换到手机侧控制。**
- 现象：用户只是想看帮助或改模型，结果可能出现以下情况之一：
  - 收到“已切换到手机侧控制”的长提示；
  - 弹出“本机忙碌等待”卡；
  - 本机启动一个 `claude` 进程，最后多半只得到“该命令在此环境不可用”这类回复（SDK 对这些命令的具体反应未确认）。
- 证据：`src/claude/runtime.ts:1146` 的注释写明，除了少数几个命令，其余都交给 Claude；话题里只拦截了 `/`、`/menu`、`/export`、`/stop`、`/deliver`、`/ls`（`1147-1165`）。
- 建议：
  - 话题里由桥接直接处理 `/help`（帮助卡）、`/model`（模型卡）、`/mode`（权限模式卡）和 `/status`（根卡片）。
  - 其他只能在终端里交互使用的 Claude Code 命令（例如 `/config`、`/login`），直接回复“只能在电脑上使用”，不切换控制权。
  - `/compact` 这类 Claude 能执行的命令照旧交给它。

**C2（中）话题里的命令出错时，用户看不到反馈。**
- 证据：
  - `onFeishuMessage` 捕获到异常后，只记录失败、再把异常抛出去（`runtime.ts:1061-1071`），不会在话题里提示。
  - 在同步范围以外的话题里发 `/export`，只会收到“正在导出完整记录…”，之后没有下文（`1025-1026`）。
  - 根卡片上“导出完整记录”按钮出错时，只记日志（`1279`）。
- 建议：在话题消息处理外面统一包一层，出错时在话题里回复“处理失败：原因”；范围外的话题明确说明不能导出。

**C3（中）服务重启后，排队等待的消息会静默丢失，提示文字还会误导。**
- 现象：
  - 等电脑上那一轮结束而排队的消息，只保存在内存里（`runtime.ts:127`）。重启后这些消息丢失，也没有任何通知。
  - 之后再点等待卡上的按钮，卡片显示“这些消息已经发送或取消”（`1395`），用户会以为消息已经发出去了。
  - 群主消息里的草稿（`128`）、`>>` 排队的消息，也是同样的情况。
- 建议：把提示改成“桥接重启过或已超时，这些消息没有发送，请重新发送”。更进一步，可以在启动时把残留的等待卡统一改成“已失效”。

**C4（中）“已切换到手机侧控制”的长提示会反复出现。**
- 现象：电脑上的 VS Code 一直开着这个会话时，两条消息只要间隔超过 10 分钟，就会再收到一次这条约 120 字的提示。
- 证据：“手机侧控制”这个状态记在会话进程上（`runtime.ts:94-95`）；进程空闲 10 分钟后会退出（`642-654`），状态随之丢失，下一条消息再次判定为“刚切换”（`771`）。
- 建议：把这个状态按会话记录下来，等电脑上有新活动时再清除。

**C5（中）几个按钮在回调里同步做了多次飞书调用，可能超过 3 秒时限。**
- 证据：
  - “打开”历史会话要读取整份会话记录，再依次发送根卡片、提问和轮次卡片（`runtime.ts:1007-1021`）。
  - 新建会话的“开始”按钮要创建话题（`860-870`，`1440-1444`）。
  - 所有飞书写操作都在一个全局队列里串行执行，每次至少间隔 220 毫秒（`feishu.ts:198-218`）。
- 影响：超时后手机提示出错，但话题已经建好；用户再点一次“开始”，可能新建出两个会话。
- 建议：回调先原地回一张“正在新建…”卡，实际工作放到后台，完成后用更新卡片的接口补上话题链接。

**C6（中）“发送本目录的文件”和“导出完整记录”点击后没有即时反馈，容易重复点击。**
- 证据：前者返回“不更新卡片”（`runtime.ts:1273-1274`），后者返回一张没有变化的根卡片（`1280`）。手机上看不出点没点上，重复点击会把最多 20 个文件发两遍。
- 建议：点击后原地显示“正在发送…”或“正在导出…”，完成后再恢复按钮。

**C7（中）打开历史会话后，搜索结果和页码丢失，也找不到新话题在哪里。**
- 证据：打开后总是换回第一页、没有搜索词的列表（`runtime.ts:1261`）。会话没有任何轮次时，点“打开”什么也不会发生（`480-481`）。
- 建议：直接回一张“已打开，[跳转到话题]”卡；打不开时说明原因。

**C8（中）`/ls` 卡片上不能直接选文件发送。**
- 现象：
  - 只有子目录有按钮，文件要靠手打 `/deliver <相对会话目录的路径>`。用按钮进入子目录以后，要打的路径会更长。
  - 卡片上写着“发送 /ls -a 查看隐藏项”，但在子目录里照做的话，列出的是会话目录，而不是当前目录。
- 证据：`src/claude/cards.ts:458-466`。
- 建议：
  - 加一个文件多选下拉框，配一个“发送选中的文件”按钮；
  - 把手打 `/ls -a` 换成“显示隐藏项”按钮。

**C9（中）群主消息里不 @ 的文字和图片被静默丢弃。**
- 证据：`runtime.ts:1099`。这个群里只有你和机器人，而且应用已经申请了接收群内全部消息的权限。另外，图片消息本身没法 @ 机器人，所以单独发一张图片新建会话这条路实际上走不通。
- 建议：在已绑定的群里，把不 @ 的群主消息也当作新会话草稿；至少回复一句“要新建会话请 @我，或回复到某个会话话题里”。

**C10（中，未确认）`/stop` 可能不会清除已经排队的消息。**
- 证据：`stopTurn` 只中断当前回合（`runtime.ts:974-983`），已经放进 SDK 输入队列的消息（`runner.ts:128-136`）没有撤回。中断后 Claude 可能马上接着处理这些消息。
- 建议：先实测 SDK 的行为。如果确实如此，`/stop` 要清空排队的消息，并在回复里说明丢弃了几条。

**C11（中，未确认）群主消息里的每条命令都会在话题群里新开一个话题。**
- 证据：群主消息的回复用的是向群里发新消息（`runtime.ts:1077-1079`），在话题群里，命令和回复会各成一个话题，把会话话题挤到下面去。
- 建议：改成回复原消息并放进它的话题里，让命令和回复留在同一个话题中。

**低优先级（Claude 侧）**
- C12：轮次卡片上没有“停止”按钮。用 `/` 调出的根卡片副本是空闲时发出的，之后不会更新，所以上面也不会出现“停止本轮”。建议在飞书侧运行中的轮次卡片上加“停止”按钮（`cards.ts:120-142`）。
- C13：每点一次“权限模式”或“模型”，都会在话题末尾新发一张设置卡，卡片越积越多（`runtime.ts:1301`）。可以改为原地替换，并加“返回”按钮。
- C14：根卡片的说明文字约 200 字，每张 `/` 副本都完整重复一遍（`cards.ts:195`）。副本可以用精简版。
- C15：控制台显示“未解决失败：N”，但在飞书里没法查看具体是什么（`cards.ts:351`）。
- C16：在根卡片副本上点“刷新”，会清掉真正根卡片的“待更新”标记（`runtime.ts:1285`）。
- C17：同步暂停时在选目录卡上选目录，会先删掉草稿再拒绝，原来写好的任务就丢了（`runtime.ts:1425`、`1441`）。
- C18：`/new <目录>` 不支持带空格的路径（`runtime.ts:1133`），`/ls` 和 `/deliver` 支持。
- C19：帮助卡没有提到“@机器人 直接写任务”这条路；`docs/claude.md` 里关于 `>>` 的两条说明被误放进了“查看和发送本机文件”一节（这是上次添加该节时我弄错的）。
- C20：暂停期间点“立即同步”，仍然提示“已开始同步”（`runtime.ts:1237`）。
- C21：`/deliver` 的敏感文件规则没有覆盖 `~/.codex/auth.json`、`~/.cache/huggingface/token`、`~/.azure`、`*_history` 等（`deliver.ts:14-16`）。只有你本人能触发这个命令，风险较低，但补上的成本很小。

### 3.3 Codex 侧

**X1（高）很多按钮的处理结果会在群主时间线另发一张新卡，被点的那张卡不变。**
- 现象：
  - 在话题里点了已经过期的批准卡或问题卡，错误提示出现在群主时间线，而不是话题里；原来那张卡的按钮还能继续点。
  - 修改会话模型时选完强度，一张会话卡被发到群主时间线，在话题群里变成一个新话题。
  - 在服务管理卡上点“暂停同步”“立即同步”“重新连接”，或者在向导里点“取消”，都会另发一整张控制台卡。原来的服务卡上仍然显示“暂停同步”按钮。
- 证据：
  - 回调结果没有指定投递方式时，`src/feishu.ts:280` 默认按“另发新消息”处理：`const delivery = outcome.delivery ?? "send"`。
  - `src/sync-runtime.ts` 里很多分支直接返回卡片，不带投递方式，例如 `1799`、`1805-1812`、`1824-1904` 之间的所有错误卡、`1892`、`1898`、`2049`、`2056-2066`、`2074`、`2077-2096`，以及兜底的 `2098`、`2102`。
  - 现有测试只检查返回的卡片内容，不检查投递方式（`test/sync.test.ts:110-140`），所以一直没有发现。
  - Claude 侧所有分支都明确写了“原地替换”，没有这个问题。
- 建议：
  - 学 Claude 侧的写法，所有分支统一走一个“原地替换”的辅助函数，`feishu.ts` 的默认值也改成原地替换。
  - 补测试，检查投递方式。
  - 另外，`feishu.ts:195` 的异步投递失败后没有人处理，也要补上。

**X2（中）几个按钮在回调里同步等待耗时操作，会超过 3 秒时限。**
- 证据：
  - “重新连接”要等模型目录刷新，最长可能需要 45 秒，还可能重启 app-server（`sync-runtime.ts:2087-2090`，`src/codex.ts:34,41`）。
  - “取消任务”要等中断完成，最长 15 秒（`1990`）。
  - “取消归档并继续”最长也要 15 秒（`2008`）。
  - `docs/design.md:42` 说路由层会把工作放到后台异步做，与实际实现不符。
- 建议：学“重发结果”的做法，先原地回一张“处理中”卡，后台完成后再更新卡片。

**X3（中）审批相关的说明和规则需要整理。**
- 现象：
  - 根卡片写着“可修改当前项目文件，不可联网”，批准卡上只有“批准一次”。按 Codex 的沙箱机制，只有在命令需要越出沙箱时才会请求批准，所以批准之后，命令可能不受沙箱限制（**未确认**，要按 Codex 0.154 的实际行为核实）。
  - README 第 136 行说“网络传输工具不能从飞书批准”，但规则只拦了 curl、wget、scp 等，`git push`、`npm install`、`pip install`、`ssh` 都能批准。
  - 规则还有误判：检测上传命令的正则前面没有单词边界，`grep "async " src` 里的 “nc ” 会被当作 netcat；检测运行时套接字路径的 `/run` 会命中 `./run.sh`。
- 证据：`src/execution-policy.ts:35-36`（已核实）、`173-179`；`src/cards.ts:167-170`、`303-318`。
- 建议：
  - 批准卡上写明批准后命令以什么权限运行；
  - 正则改为按单词匹配；
  - 决定 `git push` 等联网操作是要拦截，还是在文档里写明可以批准。
  
  这一条涉及安全策略，改之前需要你确认方向。

**X4（中）从手机新建会话后，群主时间线的状态卡一直停在“已排队”，首条任务还会被补发一次。**
- 现象：
  - 提交后会收到“已提交”和“已排队”两张卡，都不会更新为“已创建”，也没有到新话题的链接。
  - 在新话题里，Codex 回复之后，还会再出现一条“用户：<首条任务>”。
- 证据：新建成功时只更新了话题里的状态卡（`sync-runtime.ts:2704-2707`）；新会话的首条任务没有登记为“已显示”（`2844`）。手机验收时已经记为待改进，目前仍未修。
- 建议：成功后把群主时间线那张卡更新为“已创建”，并附上话题链接；新会话的首条任务也登记为“已显示”。

**X5（中）“在聊天中输入”任务：没有专门的等待卡，不能取消，过期后静默丢弃。**
- 现象：
  - 点了这个按钮后，只收到一张完整的控制台卡，第 4 步的卡片还能继续点（验收时你点了三次）。
  - 超过 10 分钟再发任务，会被静默忽略。
  - 在机器人卡片下面的话题里回复任务，或者只发一张图片，也会被静默忽略。
- 证据：`sync-runtime.ts:1907`、`2144-2147`。
- 建议：
  - 原地换成“等待你发送任务”卡，列出已选的项目、模型、强度和失效时间，并带“取消”按钮；
  - 向导过期后，或者在非会话话题里收到文字时，回一句提示。

**X6（中）修改会话模型后，根卡片不刷新，卡片上的信息也不对。**
- 现象：
  - 改完模型后，话题顶部的根卡片还显示旧的模型和强度，要等服务重启才会更新。
  - 修改模型时，模型卡上显示“强度：未选择”，强度卡上显示“项目：未选择”。
- 证据：`sync-runtime.ts:1888-1893`、`2446-2447` 没有更新根卡片；`src/cards.ts:103` 没有传入强度；会话模式的向导没有设置项目目录（`1923`、`2426`）。
- 建议：保存后更新根卡片，并把强度卡原地换回会话卡；卡片摘要里传入当前强度和会话目录。

**X7（中）批准请求只有“批准一次”，没有“本会话都允许”。**
- 证据：处理逻辑其实已经支持“本会话都允许”（`sync-runtime.ts:1193-1199`），只是卡片上没有这个按钮（`src/cards.ts:306-310`）。同类命令每次都要在手机上点一遍。Claude 侧有这个按钮。
- 建议：当 Codex 提供“本会话都允许”这个选项时，在卡片上显示对应按钮。

**X8（中）电脑上正在使用这个会话时，飞书消息排队却不说明原因，也没有处理办法。**
- 证据：`src/task-scheduler.ts:37`；状态卡只写“已排队：消息已进入会话队列”（`sync-runtime.ts:2554`）。Claude 侧这种情况会给出“立即切换、分叉、取消”三个选择。
- 建议：判定是电脑在占用时，状态卡写明“等待电脑上的 Codex 结束这一轮”，并至少提供“取消”按钮。

**X9（中）运行状态卡显示的状态不准。**
- 证据：
  - 回答了批准或提问之后，状态卡一直停在“等待批准”或“等待输入”，直到本轮结束（`resolveRemoteRequest`，`sync-runtime.ts:1174-1210`，没有更新状态卡）。
  - 1 秒内的非最终状态更新会被直接丢掉，之后也不补发（`1503`、`1517`）。所以新会话的状态卡常常停在“正在启动首个回合”。
- 建议：请求处理完后，把状态卡改回“运行中”；更新太频繁时延后合并发送，不要直接丢弃。

**X10（中）运行中不能切换 Plan/Default，与卡片上的提示矛盾。**
- 证据：`src/cards.ts:205` 写着“修改模型或模式从下一轮开始生效”，但 `sync-runtime.ts:1939` 在运行中直接报错，而且错误卡还会因为 X1 被发到群主时间线。
- 建议：允许切换，从下一轮开始生效，与修改模型的处理一致。

**X11（中）点了“告诉 Codex 怎么做”之后就没有退路。**
- 现象：
  - 批准卡被换成一张说明卡，上面没有任何按钮，无法再回去批准或拒绝。
  - 如果一直不回复，30 分钟后请求超时，卡片显示“已拒绝或取消”，看起来像是你自己拒绝的。
  - 同时有两个请求在等时，指导可能会对应到另一个请求上。
- 证据：`sync-runtime.ts:2063-2069`、`2247-2249`、`1151-1155`、`1209`；`src/db.ts:522-526`。
- 建议：说明卡上保留“批准一次”和“拒绝”按钮；按指导记录本身查找对应的请求；超时单独写成“超时自动拒绝”。

**X12（中）“查看本轮审阅”可能没有任何反应，或者显示的是旧回合。**
- 证据：
  - 审阅卡最多 24 项，每项最多 2000 字，很容易超过卡片 30 KB 的上限，发送失败后只记日志（`src/cards.ts:333-341`）。
  - 进程崩溃时遗留的“运行中”回合记录会一直被当作当前回合（`src/db.ts:455`）。验收时就遇到过一条 9 月 22 日的旧记录。
- 建议：审阅内容按字节截断；启动时把遗留的“运行中”回合标记为已中断。

**X13（中）在手机上新建会话，步骤太多。**
- 证据：
  - 项目卡列出最近 50 个目录，每个目录一个按钮（`sync-runtime.ts:1760`）。
  - 即使已经配好默认模型和强度，也必须依次点模型、再点强度（`1847`）。
  - 在群主消息里 @机器人 写任务会被拒绝（`2884-2886`），Claude 侧则直接进入选目录。
  - `/new` 不支持 `~` 开头的路径（`src/path-policy.ts:6`）。
- 建议：
  - 项目最多列 8 到 10 个，其余的靠搜索；
  - 加一个“使用默认模型和强度”按钮，直接跳到最后一步；
  - 在群主消息里 @机器人 写的文字，和 Claude 侧一样作为草稿处理。

**低优先级（Codex 侧）**
- X14：项目名、模型名、搜索词里的转义符会原样显示出来，例如 `gpt\-5\.5`（`src/cards.ts:14`、`92`、`134`、`148`、`336`）。F11 只修了会话卡。
- X15：文档、帮助与代码不一致：
  - README 写“超过 50,000 字符”，实际阈值是 25,000 字节；
  - README 说 `/status` 会显示允许目录，实际显示的是控制台；
  - README 提到的“刷新状态”“重试失败任务”按钮并不存在；
  - 权限说明卡写着“目录之外的写入会交给你批准”，实际会被自动拒绝。
- X16：同一操作在不同入口的前置检查不一致。卡片上的“新建”会检查是否暂停、模型目录是否可用；`/new`、@新建、菜单则不检查，暂停状态下可以把向导一直走到最后一步才报错。
- X17：服务重启后，“取消归档”卡的两个按钮都会显示“已过期”，但这个任务一直停在等待状态，也不会重新发卡（`sync-runtime.ts:2005`、`2016`）。
- X18：模型目录读不到时，提示让你“发送 /model”，而 `/model` 又提示“模型目录暂不可用”（`2890-2892`、`2425`）。CLI 版本太旧导致缺少新模型时，提示让你 `/retry`，但这样刷新没有用，应该改为提示升级 Codex CLI。
- X19：取消任务时，状态卡更新了，又另外回复一张状态卡或一条文字，信息重复（`1993-1999`、`2987-2988`）。
- X20：在话题里发 `/new`、`/projects`，显示的是“未知命令”，应该提示“请在群主消息里新建”。
- X21：运行中追加的消息带的图片超过大小限制时，错误只记日志，用户收不到任何回复（`2912`）。

## 四、两侧差异对照

| 功能 | Claude 侧 | Codex 侧 | 建议 |
|---|---|---|---|
| 按钮结果 | 原地替换；过期时显示“请求已失效” | 很多结果另发到群主时间线 | Codex 改为原地替换（X1） |
| 群主消息直接写任务 | @ 后写文字，再选目录 | 被拒绝，只能用 `/new` 或 4 步向导 | 对齐 Claude 的做法 |
| `/new` 的参数 | 支持带或不带目录、任务，支持 `~` | 只支持不带参数，或同时给目录和提示；不支持 `~` | 对齐 |
| 新建时选择模型 | 使用默认值，之后可以改 | 每次都要选模型和强度两步 | 加“使用默认” |
| 停止本轮 | `/stop`；根卡片上有“停止本轮” | `/cancel`；只有运行状态卡上有按钮 | Codex 加 `/stop` 作为别名 |
| 权限请求 | 允许、本会话都允许、拒绝 | 批准一次、拒绝、取消回合、告诉 Codex 怎么做 | Codex 加“本会话都允许”（X7） |
| 电脑和手机同时使用 | 等待卡，可以立即切换、分叉或取消 | 只显示“已排队” | Codex 至少说明原因并提供取消（X8） |
| 运行中补充消息 | 默认在当前这一步结束后交给 Claude；用 `>>` 可以排到本轮结束后 | 总是并入当前回合 | 可以保持现状 |
| 查看、发送本机文件 | `/ls`、`/deliver` | 没有 | 可以移植到 Codex 侧 |
| 导出完整记录 | `/export` | 没有，只有单轮附件 | 可以移植 |
| 刷新根卡片 | 有按钮 | 有处理逻辑，但没有按钮 | 加按钮 |
| 话题里的未知斜杠命令 | 交给 Claude | 显示命令菜单 | 有意的设计，各自保持即可 |

## 五、建议的实施顺序

1. **第一批（改动小，收益大）**
   - X1：Codex 统一原地替换，并补测试；
   - C1：Claude 话题内由桥接处理 `/help`、`/model`、`/mode`、`/status`；
   - C2：话题内出错时给出提示；
   - C6：发送和导出时给出即时反馈；
   - S1：文档里写明需要手工配置菜单，以及各自的事件键；
   - X14、X15、C19：文案和文档修正。
2. **第二批（防止超时导致重复执行）**
   - C5、X2：耗时操作改为先回复“处理中”，再在后台执行；
   - C3：重启后正确提示等待中的消息已失效。
3. **第三批（Codex 状态和流程）**
   - X4、X5、X6、X9、X10、X11、X12。
4. **第四批（手机端便利）**
   - C8：`/ls` 上直接选文件发送；
   - C9：群主消息不 @ 也能用；
   - X7：加“本会话都允许”；
   - X8：说明电脑占用的原因并提供取消；
   - X13：精简新建流程；
   - 把 `/ls`、`/deliver`、`/export` 移植到 Codex 侧。
5. **需要你先定方向**
   - X3：审批规则怎么处理 `git push` 等联网操作；
   - C10：`/stop` 是否丢弃排队的消息（需要先实测）。

## 六、不值得做的点

- 多选题改成复选表单：回复“1,3”已经够方便，这类问题也很少出现。
- 让所有根卡片副本自动更新：要追踪多条消息，还会引入新的竞态问题。C12 用轮次卡片上的“停止”按钮解决更简单。
- 把中文“停止”当成 `/stop`：会误伤正常对话里的这个词。
- Codex 状态卡和回复卡合并成一张：牵涉流式卡片的生命周期，改动大、风险高。
- 控制台上“项目”和“新建会话”重复、`codex.search` 和 `codex.sessions` 的效果相同：只是看起来冗余，不会造成错误。
- `hello.md` 在飞书里被识别成链接：这是飞书客户端的行为，服务端很难规避。
- Root 模式重启后授权卡不更新：Root 模式很少用，而且失败时是拒绝执行，不会误放行。
